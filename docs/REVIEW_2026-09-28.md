## Confirmed source findings

1. Both `nav_items.dart` and `role_menus.dart` expose Reviews to SUPER_USER and ADMINISTRATOR. The requested navigation restriction must cover both menu systems.
2. Calendar days only select the displayed day's event list. There is no day long-press handler or event-creation popup triggered by day selection. Existing event cards do open detail dialogs.
3. Calendar forms check admin roles, but router restrictions explicitly block calendar subroutes only for guardians. Other non-admin roles can reach the form's denial screen.
4. Calendar range queries filter by start timestamp only. An event beginning before a displayed month and ending within it will be omitted. Month boundaries are built in UTC although calendar dates are displayed locally.
5. Checked-in calendar RLS migrations permit staff to manage their own events and grant broader privileged access. Admin-only database enforcement is not established. The deployed policies have not been inspected.
6. Academic-year creation requires a Form and stores `term` and `termname`; labels include a Form rather than a two-year span.
7. Academic-year Add buttons are visible regardless of the list page's `canEdit` flag.
8. Academic-year schema requires a term and has uniqueness on `(academicyear, term)`. Removing the Form selector alone would not make the data model independent of terms. Existing term records and referencing grades, class assignments, fees and histories require a deliberate compatibility/migration strategy.
9. Guardian report cards aggregate results by year and term. Preserve this reporting distinction when decoupling academic-year labels from Forms.
10. `/academics/assignments` implements teacher/class/subject allocation, not the homework/submission/grading feature described in the supplied checklist.
11. Calendar currently provides a month grid plus selected-day events; the checklist's separate week/day views are not implemented by this page.

## Proposed change scope awaiting design confirmation

- Admin day selection opens an event editor popup. It supports one or several selected dates, title, start/end times and full description; selected nonconsecutive dates become separate occurrences. Continuous multi-day events retain start/end dates. Validate finish after start, persist before announcing success, and refresh affected calendar views.
- Every authenticated role can long-press a day to view its events and full details. Keep a normal tap-accessible detail action for mouse/keyboard users. Only admin roles get mutation controls; database policies must enforce the same rule.
- Fetch all events overlapping the local displayed month, including events that start in a previous month.
- Selecting starting year 2026 derives and displays `2026/2027`. Academic-year identity and labels are independent of Forms. Preserve existing term-based report data and foreign-key relationships through an explicit migration/compatibility design before changing storage.
- Keep Reviews only in Head Teacher navigation in both menu systems.
- Verify new event selection, long-press details, year labels, month overlap, permissions, and existing report-card behavior with meaningful tests and live role checks.

Alternative approaches considered: retain separate creation pages (more navigation), or support only continuous date ranges (cannot represent nonconsecutive selected dates). The popup supporting individual dates is recommended for the request.
